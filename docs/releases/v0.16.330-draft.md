完成 version bump 后，target-mode readiness 使用 `v0.16.329..HEAD`；创建本地 tag 后，release-tag mode 校验实际发布起点 `v0.16.329..HEAD`。

## 用户价值

- candidate issue 审计无法连接 GitHub API 或网络时返回可重试的 `E_GITHUB_UNAVAILABLE`，并明确说明尚未读取远端 issue 状态。
- 维护者不会把远端读取失败误判为 `missing`，也不会在未读取远端状态时进入 `--apply`。

## 案例库映射

- active 和 candidate 案例状态不变；三个 candidate 的 adapter package、metadata validation、online smoke 仍 pending。
- 最近真实 live preflight 返回 retryable `E_LLM_UNAVAILABLE`；不运行 candidate `explore`，也不生成或宣称 adapter asset。
- 本轮不创建、关闭或改写任何公网 issue。
- 依据 `cases/README.md`、`cases/manifest.json` 和 `search-extraction-gap` 的现有案例目录，candidate 晋级仍要求完整 package、metadata validation 和 online smoke 证据。
- `llm_live_preflight_not_ready` 仍是当前 live gate 边界；没有真实成功的 doctor JSON，不把 candidate 任务写成可执行或已验证。

## 风险与兼容性

- 仅增加 GitHub 传输故障的结构化诊断；current、stale、missing、duplicate、unexpected 审计语义保持不变。
- `--apply --confirm-rewrite` 仍需要成功读取远端 issue，Doctor evidence 仍需要当前 `--doctor-json`。

## 发版前验证

- 运行 `pytest tests/test_audit_candidate_issues.py -q --no-cov` 与 `CLIANY_QA_OFFLINE=1` 全量测试。
- 运行 `node --check site/script.js`、Ruff、Mypy、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check dist/*`。
- 运行 `python scripts/release_readiness.py --strict --target-version 0.16.330 --remote --remote-name origin`。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 创建 `v0.16.330`，运行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag 并修复，不继续发布。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 `vercel inspect www.cliany.site`、`vercel inspect cliany.site` 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
