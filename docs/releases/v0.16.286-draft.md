# v0.16.286 发布草案

**目标版本：** `0.16.286`
**提交范围：** `v0.16.285..HEAD`
**发布主题：** 让 doctor 推荐的 active demo 静态验证能够真正阻断失败后的只读执行。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.286..HEAD`；该锚点不改变实际 release diff。

## 用户价值

`doctor` 的 active demo `recommended_commands` 现在使用 `cliany-site verify <domain> --strict --json`。未安装目标仍先固定 HTTPS + SHA-256 安装；已占用目标仍不会重复安装。两种路径都会在进入只读 adapter 命令前要求严格验证成功，因此顺序 shell 自动化能通过非零退出码停止，而不再把静态失败当作可继续的诊断输出。

默认 `verify` 保持其诊断兼容性：它会报告结果，并保留退出码为零的历史契约。只有显式 `--strict` 才在任一结果 `verdict != ok` 时返回 `ok=false` 和非零退出。失败 envelope 把完整 `results` 和 `failed_domains` 保留在 `error.details`，既可阻断后续步骤，也不丢失修复信息。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 继续定义四个 active case、三个 candidate package-search case，以及已知缺口 `search-extraction-gap`。
- 本版不创建、下载、安装、覆盖或声明任何 candidate adapter asset；已发布 active demo 仍使用 release 固定 HTTPS、SHA-256、严格 verify 和只读命令。
- `llm_live_preflight_not_ready` 仍然约束 candidate 晋级；没有真实 live preflight、adapter package、metadata validation 和 online smoke 证据时，candidate 保持 pending/blocked。

## 变更分组

### 严格验证门禁

- `verify --strict` 在 schema、legacy adapter、安全扫描、manifest 或请求的 smoke 检查失败时返回非零，并在 `error.details.results` 保留诊断。
- 纯 smoke 失败使用 `E_VERIFY_SMOKE`；其他严格静态失败使用 `E_VERIFY_STATIC`。
- `demo_adapter_quickstart` 新增 `strict_verify_command`；`recommended_commands` 使用该命令，兼容的 `verify_command` 与 `commands` 不变。
- 首次成功路径、README 和官网说明只有严格验证成功后才运行只读 demo。

## 风险与兼容性

- `--strict` 是 opt-in，不改变默认 `verify` 的退出码或成功 envelope。
- `strict_verify_command` 是新增 JSON 字段；严格 key-set 校验的调用方应接受它，而继续执行 doctor 建议的调用方应消费 `recommended_commands`。
- `verify --strict` 证明本地静态状态和可选 CDP smoke，不证明第三方站点在线、登录态有效或业务命令一定返回数据。
- 本版不会运行、下载、修复、覆盖或删除 adapter，更不会伪造 live LLM、candidate package、metadata validation 或 online smoke 成功。

## 发版步骤

1. 在允许发布的日期完成版本、CHANGELOG、官网基线、reviewed GitHub Release Notes 和本草案，在干净 HEAD 运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.286`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.286 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.286`。
5. 运行 `gh release edit v0.16.286 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.286-github-release.md`，再用 `gh release view v0.16.286 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。
