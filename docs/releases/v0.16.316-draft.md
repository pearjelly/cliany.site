完成 version bump 后，target-mode readiness 使用 **提交范围：** `v0.16.316..HEAD` 作为占位锚点；创建本地 tag 后，release-tag mode 检查实际发布起点 **提交范围：** `v0.16.315..HEAD`。实际 release diff 是 `v0.16.315..v0.16.316`。

## 用户价值

v0.16.316 让 tag Release workflow 直接使用仓库中的已审阅 GitHub Release Notes 创建正式 Release，而不是先发布 compare-only 自动正文、再由维护者事后修复。严格 readiness 会在创建 tag 前要求 `docs/releases/vX.Y.Z-github-release.md` 存在、版本标题匹配且含用户可读正文，并拒绝 workflow 中的 `--generate-notes`。

这让 GitHub Release、PyPI 和最终 strict publication audit 从同一份版本化说明出发；说明缺失或错误会在 tag 之前停止，不会把 PyPI 发布后的人工补救当作正常发布步骤。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 的 8 个案例状态不变；本版不生成、安装或晋级 candidate adapter。
- `search-extraction-gap` 仍是已知缺口，本版不修改 browser、提取、adapter runtime 或在线 smoke。
- 2026-08-12 的真实 live preflight 仍为 retryable `E_LLM_UNAVAILABLE`，归类为 `llm_live_preflight_not_ready`；本地 `local_ready=true`、`local_blockers=[]`，整体 gate 仍是 blocked。
- 因此不声称 candidate package、metadata validation、online smoke、浏览器 replay 或 live LLM 成功。

## 风险与兼容性

- Release workflow 新增 checkout，只读取当前 tag 中版本化说明文件；不会变更构建 artifact 或 PyPI trusted publishing。
- 已有版本的 GitHub Release 不会被回写；新 tag 若没有已审阅说明会在 preflight 前被 readiness 拦截。
- 本版不改变 CLI、SDK、HTTP API、adapter schema 或 `doctor` 的 live LLM gate。

## 发版步骤

1. 完成版本、CHANGELOG、官网与已审阅 GitHub Release Notes finalization，并保持工作树干净。
2. 推送最终 master，等待该 HEAD 的 GitHub CI 与 Embodied CI 均成功。
3. 仅在双 CI 成功后创建本地 `v0.16.316` tag，并运行 strict `--release-tag` readiness（含 remote）。
4. 推送 tag，等待 Release workflow 使用 `docs/releases/v0.16.316-github-release.md` 创建 GitHub Release 并发布 PyPI，逐版本核验两者。
5. 将 `site/` 部署到明确链接的 `cliany.site` Vercel production 项目，浏览器检查 `www.cliany.site`。
6. 运行 strict publication audit；任一证据失败都不宣称发布完成。
