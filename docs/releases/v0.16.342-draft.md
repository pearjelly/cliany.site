## 用户价值

- HTTP 集成调用 `GET /adapters?detail=` 时，现在和 `GET /doctor?llm_live=` 使用同一套布尔参数契约：只接受 `true`/`false`、`1`/`0` 或 `yes`/`no`。
- 拼写错误或不明确的 `detail` 值现在返回 `BAD_REQUEST` / HTTP `400`，不会静默退回简略 adapter 列表，便于客户端及时发现响应形状与预期不一致。

## 证据边界

- 本轮只收紧 HTTP API 的本地查询参数校验，不改变 CLI、adapter、SDK、Chrome、LLM、案例状态或第三方工作流的就绪状态。
- 最近真实 `cliany-site doctor --llm-live --require-capability generate_adapters --json` 仍返回可重试的 `E_LLM_UNAVAILABLE`；不运行 candidate `explore`，不生成或宣称 candidate package、metadata validation、online smoke、live LLM 或第三方成功。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 保持案例目录为 8 total、4 active、3 candidate、1 known-gap；三个 candidate 的 adapter package、metadata validation、online smoke 仍 pending。
- `search-extraction-gap` 保持 known-gap；`llm_live_preflight_not_ready` 仍是 candidate 晋级前必须修复或重试的 live provider 边界。
- 本轮不修改案例目录，不创建、关闭或改写公网 issue；没有当前 doctor JSON 时也不执行 `--apply --confirm-rewrite`。

## 风险与兼容性

- 省略 `detail` 仍返回既有简略列表；所有既有合法 true/false、1/0、yes/no 拼写保持可用。
- 只有此前被静默视为 false 的无效 `detail` 值改为明确 `400`，避免自动化错把少字段成功响应当作详情列表。
- 这是本地 API 契约修复，不表示 Chrome、LLM、candidate adapter 或第三方站点已可用。

## 发版前验证

- 运行 SDK/API、发布说明与官网文档 focused tests、`CLIANY_QA_OFFLINE=1` 全量测试、Ruff、Mypy、`node --check site/script.js`、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check`。
- 版本最终化后运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --target-version 0.16.342 --remote`；创建本地 tag 后运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.342 --remote --remote-name origin`。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 运行 `git tag v0.16.342`，再执行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag 并修复。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 alias inspect 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
