# v0.16.296 发布草案

**目标版本：** `0.16.296`
**提交范围：** `v0.16.295..HEAD`
**发布主题：** 让 HTTP API 调用方能够稳定区分请求错误、缺失资源与暂不可用依赖。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.296..HEAD`；该锚点不改变实际 release diff。

## 用户价值

HTTP API 以前只在缺少字段或无法解析 JSON 时返回 `400`。JSON 数组、错误类型的 `params`，以及字符串 `"false"` 这类写操作控制参数，可能被服务器当成内部失败，或意外转换为真值。SDK 已经提供结构化 error envelope，但 HTTP 调用方无法从状态码可靠地区分“修正请求”“安装 adapter”与“稍后重试 provider”。

本版要求所有写操作端点接收 JSON 对象；`params` 必须是对象，`force` 和 `dry_run` 必须是布尔值。API 保留 SDK 的 `{success, data, error}` envelope，并把缺失 adapter/command 映射为 `404`、可重试的 Chrome/LLM 不可用映射为 `503`、可表达但无法完成的工作流结果映射为 `422`。双语 README 与官网文档同时给出可运行的 `asyncio.run(main())` SDK 入口和状态码契约。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 仍包含四个 active case、三个 candidate package-search case 和一个 `search-extraction-gap`；candidate 的九项 promotion evidence 仍为 pending。
- 2026-08-03 最近一次真实 `doctor --llm-live --require-capability generate_adapters --json` 仍因 provider connection error 返回可重试 `E_LLM_UNAVAILABLE`；本版仅把该 SDK/API 类错误在 HTTP 中稳定映射为 `503`，不运行 candidate `explore`，不生成、安装或发布 candidate adapter package，也不声称 metadata validation 或 online smoke 成功。
- `llm_live_preflight_not_ready` 仍是 candidate adapter-package 路径的 blocker；只有严格预检变为 ready 后才能开始真实 `explore`。
- `scripts/audit_candidate_issues.py --repo pearjelly/cliany.site --json` 必须继续确认公开 candidate issues #14、#15、#16 为 current；本地 provider 错误不是外部成功证据。

## 风险与兼容性

- 成功响应和 SDK JSON envelope 字段不变；HTTP 状态码只为现有错误码增加传输层语义。
- 以前错误地提交 JSON 数组、非对象 `params` 或字符串控制参数的客户端现在会得到明确 `400`，而不再依赖 Python 真值转换或 `500`。
- 未映射的异常仍为 `500`；本版不假设所有 adapter 运行时错误可安全重试。
- 本版不代表 live LLM、candidate workflow、candidate adapter package 或第三方站点操作成功。

## 发版步骤

1. 在干净 HEAD 完成版本、CHANGELOG、官网基线、路线图、reviewed GitHub Release Notes 和本草案，并运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.296`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.296 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.296`。
5. 运行 `gh release edit v0.16.296 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.296-github-release.md`，再用 `gh release view v0.16.296 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

## Release Notes 摘要

`v0.16.296` makes HTTP API errors actionable through strict request validation and stable status codes while preserving the SDK envelope, without claiming a live provider or candidate workflow succeeded.
