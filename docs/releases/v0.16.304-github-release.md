# v0.16.304

Verify an installed adapter before an integration schedules browser work.

## What Changed

- Added asynchronous `ClanySite.verify(domain)` and synchronous `verify(domain)` helpers.
- Added `GET /verify?domain=<domain>` for service-to-service adapter readiness checks.
- Verification returns the same strict `results` and `failed_domains` diagnostics used by the CLI, without opening Chrome or contacting an LLM.
- Invalid path-shaped, NUL-containing, or non-string adapter names are rejected before the runtime loader runs. SDK and CLI return `E_INVALID_PARAM`; HTTP returns `400`.
- The strict banned-pattern and UTF-8 checks run before `commands.py` is imported, returning `security_issue` / `E_VERIFY_STATIC` and HTTP `422` for a rejected or unreadable module.

## Compatibility

Valid single-directory adapter names and existing error envelopes remain compatible. `GET /verify` follows the established API status mapping: `404` for an absent adapter and `422` for a static verification failure. Existing health, doctor, adapter-listing, and mutation endpoints are unchanged.

## Trust Boundaries

Verification does not prove that a browser workflow, third-party site, GitHub Release, PyPI publication, live LLM provider, or candidate adapter package is ready. It does not use CDP or an LLM, but it loads the installed adapter module to confirm the runtime loader contract; only verify adapters that are already installed and trusted. Candidate promotion remains pending until its required evidence is collected and verified.

## Verification

Focused SDK/API, path-safety, and website-content regressions, full offline tests, package build and Twine validation, required CI, GitHub Release, PyPI, Vercel production deployment, website browser inspection, and strict publication audit are required before release completion.
