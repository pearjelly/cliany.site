# v0.16.279 发布草案

**目标版本：** `0.16.279`
**提交范围：** `v0.16.278..HEAD`
**发布主题：** 让开放的 candidate promotion issue 与当前严格 preflight 契约保持一致，避免贡献者从陈旧 issue body 获得过期命令。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.279..HEAD`；该锚点不改变实际 release diff。

## 用户价值

candidate issue 是外部贡献者看到的可执行交接入口。即使 `cases --issue-template` 已修正，已经创建的 issue body 仍可能保留旧命令，诱导贡献者在真实 `explore` 前跳过严格 live LLM gate。

本版增加 `scripts/audit_candidate_issues.py`：默认只读比较当前 manifest 所列 candidate 对应的开放 `case-proposal` issue title、body 与当前生成 template，输出 `current`、`stale`、`missing` 或 `duplicate` 和可复核的 SHA-256。只有 `--apply --confirm-rewrite` 才会重写已经匹配且 stale 的 body；遇到 missing 或 duplicate 时不创建、关闭或猜测处理方式。

2026-07-27 的真实 preflight 仍返回 `E_LLM_UNAVAILABLE`（OpenAI-compatible provider connection error），Chrome/CDP 和已有 adapter 路径可用，但 `generate_adapters.ready=false`。因此本版没有运行真实 explore、没有生成 adapter package、没有进行 online smoke，也不声称第三方站点或 live LLM 成功。

在该真实 blocker 下，已审阅并刷新 public issue #14、#15、#16；它们现在都使用 `cliany-site doctor --llm-live --require-capability generate_adapters --json` 作为 candidate `adapter_package` 的首条可执行命令。

## 变更分组

### Public issue contract audit

- 新增 `python scripts/audit_candidate_issues.py --repo pearjelly/cliany.site --json`，只读审计候选 issue body 与当前 `cases --issue-template` 输出。
- 报告逐 case 输出当前期望 body SHA-256、实际 body SHA-256、issue URL 和状态；`--case-id` 可缩小审计范围。
- `--apply` 必须配合 `--confirm-rewrite`，并且只在没有 missing/duplicate 的情况下重写 stale body 后重新抓取 GitHub 验证。

### Contributor handoff

- 案例库、每周维护循环、公开路线图和官网文档都增加公开 issue freshness 的只读检查与显式重写边界。
- 已刷新三条公开 candidate issue，修复历史 `doctor --llm-live --json` 交接命令；案例仍为 candidate，未被提前标记 active。

## 案例库映射

- `cases/manifest.json` 和 [cases/README.md](../../cases/README.md) 仍定义四个 active case、三个 candidate package-search case，以及已知缺口 `search-extraction-gap`。
- 三个 candidate 的首个证据任务仍是 `adapter_package`；本次只让它们的公开 issue 重新指向相同的 strict preflight，并不改变 manifest status 或 promotion evidence。
- 2026-07-27 的 provider 连接失败继续按 `llm_live_preflight_not_ready` 处理：它是可复核 blocker，而不是可以跳过的 explore 前置条件。

## 风险与兼容性

- 该脚本需要已认证的 GitHub CLI；离线 CI 不调用它，测试只覆盖纯审计逻辑。
- 默认审计不会修改 GitHub 状态。`--apply --confirm-rewrite` 会替换已匹配 stale issue 的 body，但不修改评论、标签、状态或案例 manifest。
- 该更新不构成 adapter package、metadata validation、online smoke 或 live LLM 成功证据。

## 发版步骤

1. 完成版本、CHANGELOG、官网基线、reviewed GitHub Release Notes 和本草案，在干净 HEAD 运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.279`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.279 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.279`。
5. 运行 `gh release edit v0.16.279 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.279-github-release.md`，再用 `gh release view v0.16.279 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

`v0.16.279` keeps public candidate issue handoffs aligned with the current strict preflight contract while preserving the boundary between an observed blocker and real adapter promotion evidence.
