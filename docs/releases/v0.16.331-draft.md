## 用户价值

- candidate issue 审计在确认某个候选 issue 缺失时，JSON 和人类报告都会给出精确的 `cliany-site cases --case-id <id> --issue-template --json` 审阅模板命令。
- 交接明确保持只读：命令只生成可审阅正文，审计不会自动创建公网 issue，避免把检测结果误当成发布授权。

## 案例库映射

- active 和 candidate 案例状态不变；三个 candidate 的 adapter package、metadata validation、online smoke 仍 pending。
- 最近真实 live preflight 返回 retryable `E_LLM_UNAVAILABLE`；不运行 candidate `explore`，也不生成或宣称 adapter asset。
- 本轮不创建、关闭或改写任何公网 issue。
- `missing` 状态来自真实远端读取结果；它与 GitHub API 不可用时的 `E_GITHUB_UNAVAILABLE` 保持区分。
- 依据 `cases/README.md`、`cases/manifest.json` 和 `search-extraction-gap` 的现有案例目录，`llm_live_preflight_not_ready` 仍是 candidate 晋级边界；没有真实成功的 doctor JSON，不把 candidate 任务写成可执行或已验证。

## 风险与兼容性

- 仅增加 missing issue 的结构化维护者交接字段和人类提示；current、stale、duplicate、unexpected 审计语义保持不变。
- 审计默认仍只读；`--apply --confirm-rewrite` 的 Doctor evidence 保护和远端读取门禁不变。

## 发版前验证

- 运行 issue-audit focused tests 与 `CLIANY_QA_OFFLINE=1` 全量测试。
- 运行 `node --check site/script.js`、Ruff、Mypy、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check dist/*`。
- 运行 `python scripts/release_readiness.py --strict --target-version 0.16.331 --remote --remote-name origin`。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 创建 `v0.16.331`，运行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag并修复，不继续发布。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 `vercel inspect www.cliany.site`、`vercel inspect cliany.site` 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
