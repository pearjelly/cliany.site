## 用户价值

- `doctor --llm-live --require-capability generate_adapters --json` 在没有 LLM key 时返回已有的 `E_LLM_DISABLED`，而 provider 上游连接失败仍返回 `E_LLM_UNAVAILABLE`。
- 两条失败路径都保留完整 `checks`、`summary` 和 capability blockers 到 `error.details`，自动化可以区分本地配置修复与上游重试，不再把两者归为同一个通用能力错误。
- README、quickstart、公开路线图和官网 `/docs` 同步了这条修复路径；live LLM preflight、candidate package 和 online smoke 门禁没有放宽。

本轮发布资料引用 `cases/README.md`、`cases/manifest.json`、`search-extraction-gap` 和 `llm_live_preflight_not_ready` 作为案例目录与候选门禁边界；这些引用不代表 candidate 已晋级。

## 案例库映射

- active 案例和 candidate 案例状态不变；candidate adapter package、metadata validation、online smoke 仍未有证据。
- 本轮真实 provider 预检仍由实际结果决定；如果返回 `E_LLM_UNAVAILABLE` 或其他 blocker，不运行 candidate `explore`，也不生成或宣称 adapter asset。

## 风险与兼容性

- 只补齐严格 doctor capability 门禁在缺少 key 时的稳定错误码和诊断字段；成功路径、普通 `doctor`、CLI adapter 命令、SDK、HTTP API、案例状态和 release workflow 不变。
- `E_LLM_DISABLED` 与 `E_LLM_UNAVAILABLE` 都是本地 readiness evidence，不代表 live LLM、candidate package、online smoke 或第三方工作流可用。

## 发版前验证

- 运行 `pytest tests/test_doctor.py -q --no-cov` 和相关 CLI/site/release regressions。
- 运行 `node --check site/script.js`、`CLIANY_QA_OFFLINE=1` 全量测试、Ruff、Mypy、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check dist/*`。
- 运行 `python scripts/release_readiness.py --strict --target-version 0.16.327 --remote --remote-name origin`。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 创建 `v0.16.327`，运行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag 并修复，不继续发布。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 `vercel inspect www.cliany.site` 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
