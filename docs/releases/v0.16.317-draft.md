## 用户价值

v0.16.317 让 `scripts/audit_candidate_issues.py` 可选接收保存的 strict doctor JSON：`--doctor-json /tmp/cliany-doctor-preflight.json`。审计会复用 `cases --issue-template --doctor-json` 的既有 extracted evidence 合成期望正文，因此旧的占位 template 不会再被误判为当前的 blocker handoff。

JSON report 会显式记录 evidence 的 `source_path`、`values_sha256`、`state_status` 和 `ready_for_adapter_package`。默认审计仍然只读；即使已提供 doctor evidence，改写公开正文也仍要求维护者先审阅 `stale` 并显式传入 `--apply --confirm-rewrite`。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 的 8 个案例状态不变；本版不生成、安装或晋级 candidate adapter。
- `search-extraction-gap` 仍是已知抽取缺口，本版不修改 browser、提取、adapter runtime 或在线 smoke。
- 当前已知的 live preflight blocker 仍是 retryable `E_LLM_UNAVAILABLE` / `llm_live_preflight_not_ready`；该版本只允许把真实保存的 JSON 作为 issue handoff evidence。
- 不运行 candidate `explore`，不声称 candidate package、metadata validation、online smoke、浏览器 replay 或 live LLM 成功。

## 风险与兼容性

- 不带 `--doctor-json` 的 audit 保持既有模板和 JSON report 契约；只在显式传入文件时加载其证据。
- 无法读取或解析的 doctor JSON 是输入错误，返回非零而不访问或改写 GitHub issue。
- `--doctor-json` 不改变 issue 生命周期：工具不创建、关闭 issue，也不将 candidate 标记为 active。

## 发版步骤

1. 按实际日期完成版本、CHANGELOG、官网和 GitHub Release Notes finalization，并保持工作树干净。
2. 推送最终 master，等待该 HEAD 的 GitHub CI 与 Embodied CI 均成功。
3. 仅在双 CI 成功后创建本地 `git tag v0.16.317`，并运行 strict `release_readiness.py --strict --release-tag v0.16.317 --remote --remote-name origin`。
4. 推送 tag，等待 Release workflow 成功，逐版本核验 GitHub Release 和 PyPI。
5. 将 `site/` 部署到明确链接的 `cliany.site` Vercel production 项目，运行 `vercel inspect www.cliany.site --wait --timeout 90s` 并进行浏览器检查。
6. 运行 `check_release_publication.py --strict --remote --distribution --json`；任一证据失败都不宣称发布完成。
