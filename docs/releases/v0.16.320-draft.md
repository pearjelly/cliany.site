完成 version bump 后，target-mode readiness 使用 **提交范围：** `v0.16.320..HEAD` 作为占位锚点；创建本地 tag 后，release-tag mode 检查实际发布起点 **提交范围：** `v0.16.319..HEAD`。实际 release diff 将是 `v0.16.319..v0.16.320`。

## 用户价值

使用 `scripts/plan_next_iteration.py --doctor-json ... --issues-dir ...` 生成候选工单时，planner 现在与 `cases --issue-template` 使用同一组公开交接语义：保存的 doctor preflight 会显示为已附加的 gate 证据，adapter package 仍明确显示为未附加；provider 暂不可用时，正文会要求等待恢复并重跑 strict preflight，而不是把旧的 package next action 展示成可立即执行的命令。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 的案例入口和 8 个案例状态保持可验证；本版只修正 planner 生成的候选 issue handoff。
- `search-extraction-gap` 仍是已知抽取缺口，本版不修改 browser、提取、adapter runtime 或在线 smoke。
- `pypi-project-search`、`npm-package-search` 和 `crates-io-crate-search` 仍是 candidate；本版不生成、安装或晋级 candidate adapter。
- 最近真实 strict live preflight 仍为 retryable `E_LLM_UNAVAILABLE` / `llm_live_preflight_not_ready`；不得宣称 candidate package、metadata validation、online smoke 或 live LLM 成功。

## 风险与兼容性

- 不带 `--doctor-json` 的 planner、issue template、审计和既有 package evidence 字段保持兼容。
- 变更只影响 planner 生成的公开 issue body，不改变 candidate 状态、严格 preflight、package acceptance 或显式 issue rewrite gate。
- 本版不创建、关闭或提前晋级 GitHub issue。

## 发版步骤

1. 按实际日期完成版本、CHANGELOG、官网和 GitHub Release Notes finalization，并保持工作树干净。
2. 推送最终 master，等待该 HEAD 的 GitHub CI 与 Embodied CI 均成功。
3. 仅在双 CI 成功后运行 `git tag v0.16.320` 创建本地 tag，并运行 `python scripts/release_readiness.py --strict --release-tag v0.16.320 --remote --remote-name origin`。
4. 推送 tag，等待 Release workflow 成功，逐版本核验 GitHub Release 和 PyPI。
5. 将 `site/` 部署到明确链接的 `cliany.site` Vercel production 项目，inspect 后进行浏览器检查。
6. 运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`；任一证据失败都不宣称发布完成。
