# v0.16.280 发布草案

**目标版本：** `0.16.280`
**提交范围：** `v0.16.279..HEAD`
**发布主题：** 让公开 candidate issue 审计能明确发现标题漂移或孤立的 `case-proposal` issue，避免维护者只看到 `missing` 而错误地重写其它 body。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.280..HEAD`；该锚点不改变实际 release diff。

## 用户价值

公开 candidate issue 是贡献者执行严格 preflight 的入口。v0.16.279 已让 body 漂移可见，但如果 issue title 被手工改名、案例从 manifest 移除，原审计会报告预期 case `missing`，却不会逐条列出那条仍带 `case-proposal` 标签的公开 issue。

本版将这种标签仍在、title 不属于当前 candidate manifest 的 issue 显式报告为 `unexpected`，并给出 issue number、实际 title、URL 与 body SHA-256。`--apply --confirm-rewrite` 在任何 `missing`、`duplicate` 或 `unexpected` 状态下都不执行，维护者必须先解决协作状态，再对已匹配的 `stale` body 做显式重写。

2026-07-27 的真实公开审计结果仍为 #14、#15、#16 三条 `current`，没有 `unexpected` issue。真实 live LLM preflight 先前仍返回 `E_LLM_UNAVAILABLE`，因此本版没有运行真实 explore、没有生成 adapter package、没有 metadata validation 或 online smoke，也不声称第三方站点或 live LLM 成功。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 仍定义四个 active case、三个 candidate package-search case，以及已知缺口 `search-extraction-gap`。
- `unexpected` 只处理开放 `case-proposal` issue 的公共交接完整性，不改变任何 case 的 manifest status、promotion evidence 或 `adapter_package` 状态。
- live provider 未就绪时继续按 `llm_live_preflight_not_ready` 处理：candidate 必须保留 pending/blocked，而不是将本次审计改进误当成 adapter package 证据。

## 变更分组

### Public issue contract completeness

- 审计输出增加 `unexpected_issue_count`、`unexpected_issue_numbers` 与每条未知 issue 的 title、URL、body SHA-256。
- 已知 candidate title 在 `--case-id` 局部审计时不会误报为 unexpected；真正不属于当前 manifest 的 label issue 才会阻止通过。
- 默认行为仍只读；没有 `missing`、`duplicate`、`unexpected` 时，显式 `--apply --confirm-rewrite` 才可重写匹配 stale body，并会重新抓取 GitHub 复核。

## 风险与兼容性

- 该脚本需要已认证的 GitHub CLI；离线 CI 不访问 GitHub，测试只覆盖纯审计逻辑。
- `unexpected` 可能暴露人工创建或改名的公开协作项；它不会猜测归属、自动改标题、创建、关闭、重新标记或晋级 issue。
- 该更新不构成 adapter package、metadata validation、online smoke 或 live LLM 成功证据。

## 发版步骤

1. 完成版本、CHANGELOG、官网基线、reviewed GitHub Release Notes 和本草案，在干净 HEAD 运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.280`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.280 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.280`。
5. 运行 `gh release edit v0.16.280 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.280-github-release.md`，再用 `gh release view v0.16.280 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

`v0.16.280` makes unexpected labeled candidate issues a visible, blocking contract state, while preserving the distinction between public-handoff maintenance and real adapter promotion evidence.
