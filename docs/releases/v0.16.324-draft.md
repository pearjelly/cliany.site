## 用户价值

- 新增一份真实日期化的 active demo evidence snapshot，记录 `issues.apache.org` 的 `cliany-site verify issues.apache.org --strict --json` 静态校验和 `cliany-site issues.apache.org list-issues --project SPARK --limit 5 --json` 只读结果。
- quickstart、公开路线图、官网首页和官网文档都指向同一份可复核证据，并明确它只是捕获时点的环境结果，不是持续服务保证。
- 这让新用户可以先复核一条已维护的只读路径，再决定是否配置 LLM；同时保留 candidate adapter、live LLM、metadata validation 和 online smoke 的严格边界。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 仍是本项目公开案例状态的来源。
- `issues.apache.org` 仍是已维护的 active demo；本版记录的实际运行返回静态 verdict `ok` 和 5 条 SPARK 只读结果。
- `pypi-project-search`、`npm-package-search` 和 `crates-io-crate-search` 仍是 candidate，公开 issue #14/#15/#16 保持 current。
- `search-extraction-gap` 仍是 known-gap；本版只记录 active demo 证据，不把候选抽取质量包装成已验证结果。
- 本轮真实 `cliany-site doctor --llm-live --require-capability generate_adapters --json` 返回 retryable `E_LLM_UNAVAILABLE` / `llm_live_preflight_not_ready`；没有 adapter package、metadata validation、online smoke 或 live LLM 成功证据，本版不晋级 candidate。

## 风险与兼容性

- 变更限于日期化证据文档、quickstart、路线图和官网内容，不改变 CLI、adapter、SDK、HTTP API、案例状态或 release workflow。
- 第三方 issue 数量、标题和状态会变化；证据文件明确要求在需要新鲜数据时重新运行命令，不应复制快照当作当前状态。
- 通过发布门禁只证明仓库和公开资料可发布，不证明 Chrome、LLM、adapter package、浏览器 workflow 或第三方服务持续可用。

## 发版前验证

- 运行 `node --check site/script.js`、相关 focused tests 和 `CLIANY_QA_OFFLINE=1` 全量测试。
- 运行 Ruff、Mypy、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check dist/*`。
- 运行 `python scripts/release_readiness.py --strict --target-version 0.16.324 --remote --remote-name origin`。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 创建 `v0.16.324`，运行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag 并修复，不继续发布。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 `vercel inspect www.cliany.site` 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
