# v0.16.288 发布草案

**目标版本：** `0.16.288`
**提交范围：** `v0.16.287..HEAD`
**发布主题：** 让严格 verify 与运行时 adapter 注册使用同一份可执行性契约。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.288..HEAD`；该锚点不改变实际 release diff。

## 用户价值

`cliany-site verify <domain> --strict --json` 现在不只确认 `commands.py` 存在、是普通文件并通过安全扫描；它还会使用与运行时 loader 相同的入口规则，确认模块可以加载且导出的 `cli` 确为 `click.Group`。此前，一个语法正确但导出普通 `click.Command` 的文件能通过严格校验，随后 doctor 引导的只读命令却无法注册 domain。现在这类安装会得到 `commands_unloadable` 与现有非零 `E_VERIFY_STATIC` 信封，顺序自动化会在业务命令前停止。

默认 `verify` 仍是诊断模式：它以零退出返回新的 verdict 与明确 issue。只有显式 `--strict` 将该静态问题转成进程失败；完整 `results` 和 `failed_domains` 保留在 `error.details`，因此已有 JSON 调用方可继续读取诊断，也能在严格路径安全停止。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 继续定义四个 active case、三个 candidate package-search case，以及已知缺口 `search-extraction-gap`。
- 本版不创建、下载、安装、覆盖或声明任何 candidate adapter asset；已发布 active demo 仍使用 release 固定 HTTPS、SHA-256、严格 verify 和只读命令。
- `llm_live_preflight_not_ready` 仍然约束 candidate 晋级；没有真实 live preflight、adapter package、metadata validation 和 online smoke 证据时，candidate 保持 pending/blocked。

## 变更分组

### 运行时加载契约

- loader 与 lazy adapter registry 复用同一 command-module 加载实现，统一处理非普通文件、无法创建 loader、导入异常和未导出 `click.Group` 的 `cli`。
- `verify --strict` 在现有 metadata、schema、安全扫描和 manifest 门禁后复用该契约；无法注册的模块返回 `commands_unloadable`，并继续使用 `E_VERIFY_STATIC`。
- doctor 不在环境检查时执行本地 adapter 代码；它继续把 `verify --strict` 作为 recommended_commands 的显式门禁，只有该命令成功时顺序脚本才执行最后的只读案例。
- 默认 `verify` 的零退出诊断契约、`verify_command`、`strict_verify_command` 与 `recommended_commands` 字段保持兼容。

## 风险与兼容性

- `commands_unloadable` 是 `verify` results 的新增 verdict；严格调用方已通过 `verdict != ok` 接收静态失败，默认诊断调用方仍得到成功 envelope 和零退出。
- 严格验证会加载本地 adapter module，以匹配运行时注册行为；它仍不能证明第三方站点在线、登录态有效或业务命令一定返回数据。
- 本版不会运行、下载、修复、覆盖或删除 adapter，更不会伪造 live LLM、candidate package、metadata validation 或 online smoke 成功。

## 发版步骤

1. 在允许发布的日期完成版本、CHANGELOG、官网基线、reviewed GitHub Release Notes 和本草案，在干净 HEAD 运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.288`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.288 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.288`。
5. 运行 `gh release edit v0.16.288 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.288-github-release.md`，再用 `gh release view v0.16.288 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。
