## 用户价值

- candidate issue 审计现在把 GitHub 明确的 HTTP 500、502、503、504 服务端或网关故障归类为可重试的 `E_GITHUB_UNAVAILABLE`。
- 维护者不会因为 GitHub 暂时返回网关错误，就把未读取到的远端 issue 状态误判成 `missing` 或进入 `--apply`。

## 证据边界

- 本轮只改进 GitHub issue 远端读取故障的分类，不创建、关闭、改写或晋级任何公网 issue。
- candidate adapter package、metadata validation、online smoke 和 live LLM 仍 pending；最近真实 preflight 为 retryable `E_LLM_UNAVAILABLE`，不运行 candidate `explore`。

## 案例库映射

- 依据 `cases/README.md` 与 `cases/manifest.json`，active 和 candidate 案例状态不变；三个 candidate 的 adapter package、metadata validation、online smoke 仍 pending。
- 本轮不创建、关闭或改写任何公网 issue；`search-extraction-gap` 仍为 known-gap。
- `llm_live_preflight_not_ready` 仍是 candidate 晋级边界；没有真实成功的 doctor JSON，不把 candidate 任务写成可执行或已验证。

## 兼容性

- `current`、`stale`、`missing`、`duplicate`、`unexpected` 审计语义不变。
- 只有明确的 GitHub HTTP 5xx、已知连接失败和 GraphQL EOF 进入可重试的 `E_GITHUB_UNAVAILABLE`；认证或普通命令错误不会被静默改写。
- 默认审计仍只读；`--apply --confirm-rewrite` 的 Doctor evidence 保护和远端读取门禁不变。

## 风险与兼容性

- HTTP 5xx 只在 GitHub issue 读取命令失败时被视为可重试；认证失败和普通 `gh` 命令错误仍按原错误路径返回。
- CLI、adapter、SDK、HTTP API、案例状态和 release workflow 不变。

## 发版前验证

- 运行 issue-audit focused tests、`CLIANY_QA_OFFLINE=1` 全量测试、Ruff、Mypy、`node --check site/script.js`、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check dist/*`。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 创建 `v0.16.333`，运行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag 并修复。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 alias inspect 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
