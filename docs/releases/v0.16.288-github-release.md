# v0.16.288

Strict verification now confirms that an installed adapter can satisfy the same Click registration contract used at runtime.

## What Changed

- `cliany-site verify <domain> --strict --json` now reports `commands_unloadable` when `commands.py` cannot load or does not export a `click.Group` named `cli`.
- The runtime loader and lazy adapter registry use the same command-module loading path, so strict verification and command registration no longer disagree about a valid adapter entry point.
- The strict result keeps the existing nonzero `E_VERIFY_STATIC` envelope, with diagnostics retained in `error.details.results`.

## Compatibility

Default `verify` remains diagnostic and exit-zero, reporting the new verdict in `data.results`. Only `verify --strict` becomes a nonzero process gate. Existing `verify_command`, `strict_verify_command`, and doctor `recommended_commands` fields remain compatible; sequential callers run the read-only command only after the strict gate succeeds.

## Trust Boundaries

This validates the local adapter module's registration shape only. It does not prove a third-party site is online, a session is valid, or a business command will return data. This release does not install, overwrite, delete, repair, download, or execute an adapter merely by running doctor or verify. It does not claim live LLM success, a candidate adapter archive, metadata validation, or an online smoke result.

## Verification

Focused verify, loader, lazy-registry, doctor, documentation, and release-doc tests; the full offline suite; package build; Twine metadata validation; required CI workflows; GitHub Release; PyPI; Vercel production deployment; browser inspection; and strict publication audit are required before this release is complete.
