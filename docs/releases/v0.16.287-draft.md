# v0.16.287 发布草案

**目标版本：** `0.16.287`
**提交范围：** `v0.16.286..HEAD`
**发布主题：** 让 doctor 推荐的严格验证在 adapter 命令文件残缺时也能停止自动化。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.287..HEAD`；该锚点不改变实际 release diff。

## 用户价值

`cliany-site verify <domain> --strict --json` 现在要求 `commands.py` 存在且可作为普通文件加载。有效 metadata 但命令文件缺失、或同名目录占位的 adapter 会得到 `commands_missing` verdict 和非零 `E_VERIFY_STATIC` 信封。doctor 推荐的 active demo 顺序脚本因此会在只读命令前停止，不再把残缺本地目录误作可运行 adapter。

默认 `verify` 保持诊断兼容性：它报告 `commands_missing` 及 issues，但继续使用零退出的历史契约。只有显式 `--strict` 把该静态问题转为非零失败；完整 `results` 和 `failed_domains` 保留在 `error.details`，供自动化和人工修复使用。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 继续定义四个 active case、三个 candidate package-search case，以及已知缺口 `search-extraction-gap`。
- 本版不创建、下载、安装、覆盖或声明任何 candidate adapter asset；已发布 active demo 仍使用 release 固定 HTTPS、SHA-256、严格 verify 和只读命令。
- `llm_live_preflight_not_ready` 仍然约束 candidate 晋级；没有真实 live preflight、adapter package、metadata validation 和 online smoke 证据时，candidate 保持 pending/blocked。

## 变更分组

### 严格验证结构门禁

- `verify --strict` 把缺失的 `commands.py` 和同名目录判为 `commands_missing`，并以现有 `E_VERIFY_STATIC` 契约非零退出。
- `strict_verify_command` 与 `recommended_commands` 保持原有 doctor JSON 字段；只有底层结构失败现在也会进入同一个严格门禁。
- 单独请求的 CDP smoke 仍在纯 smoke 失败时使用 `E_VERIFY_SMOKE`，不改变已有严格验证错误分类。
- 默认 `verify` 继续返回诊断结果与零退出，避免破坏已依赖其报告模式的调用方。
- README、10 分钟指南、路线图和官网文档说明：doctor 的 `recommended_commands` 只有在命令文件可加载时才会进入只读 demo。

## 风险与兼容性

- `commands_missing` 是 `verify` results 的新增 verdict；严格调用方已通过 `verdict != ok` 接收静态失败，默认诊断调用方仍保持成功 envelope 和零退出。
- 验证命令文件存在与可加载不证明第三方站点在线、登录态有效或业务命令一定返回数据。
- 本版不会运行、下载、修复、覆盖或删除 adapter，更不会伪造 live LLM、candidate package、metadata validation 或 online smoke 成功。

## 发版步骤

1. 在允许发布的日期完成版本、CHANGELOG、官网基线、reviewed GitHub Release Notes 和本草案，在干净 HEAD 运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.287`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.287 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.287`。
5. 运行 `gh release edit v0.16.287 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.287-github-release.md`，再用 `gh release view v0.16.287 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。
