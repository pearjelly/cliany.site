# v0.16.278 发布草案

**目标版本：** `0.16.278`
**提交范围：** `v0.16.277..HEAD`
**发布主题：** 为真实 adapter 生成预检增加严格能力门禁，让不可用的 live LLM 以非零退出码阻止自动化继续，同时保留可审阅的 blocker evidence。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.278..HEAD`；该锚点不改变实际 release diff。

## 用户价值

普通 `cliany-site doctor --llm-live --json` 是诊断命令：它会把 live provider 不可用显示为 warning，并保留已有 adapter 是否可运行的结论。这适合人工排查，但只检查进程退出码的维护脚本可能把 `ok=true` 误解为可以继续生成 adapter。

本版新增 `--require-capability`。candidate 晋级和长时间 `explore` 使用 `cliany-site doctor --llm-live --require-capability generate_adapters --json` 时，CDP、目录、LLM 配置或 live LLM 任一 blocker 都会使命令以非零退出；live 上游不可用会保留原始 `E_LLM_UNAVAILABLE`，而不是模糊为通用失败。`generate_adapters` 的严格门禁要求显式 `--llm-live`，避免只检查 key/config 就把未验证的 provider 当作 ready。

2026-07-26 的真实 preflight 证据是：Chrome/CDP 与已有 adapter 路径可用，但 OpenAI-compatible provider 返回可重试的 `E_LLM_UNAVAILABLE`（connection error），`generate_adapters.ready=false`。因此本版没有运行真实 explore、没有生成 adapter package、没有进行 online smoke，也不声称第三方站点或 live LLM 成功。

## 变更分组

### Strict preflight gate

- `doctor --require-capability manage_adapters|run_browser_workflows|generate_adapters` 现在可把未就绪能力转成结构化失败 envelope 和非零退出码。
- `generate_adapters` 的严格 gate 必须配合 `--llm-live`；缺少该参数返回 `E_INVALID_PARAM`，防止配置检查替代真实上游预检。
- gate 会优先保留 blocker 的具体错误码，例如 `E_LLM_UNAVAILABLE`；完整 doctor payload 放在 `error.details`，供脚本和人工复核。

### Candidate evidence handoff

- candidate 的 executable preflight command、template、promotion plan、validator、planner、公开维护文档和官网交接文字统一为严格能力 gate。
- `cases --doctor-json`、`plan_next_iteration.py --doctor-json` 与 `extract_doctor_preflight_evidence.py` 现在都能读取严格失败 envelope 的 `error.details`，继续生成 blocked evidence，而不是因顶层 `ok=false` 丢失事实。
- `cases/README.md`、`cases/manifest.json` 和 `search-extraction-gap` 的 candidate/known-gap 真实性边界不变；没有真实 adapter package、metadata validation 和 online smoke 就不会晋级。

## 案例库映射

`pypi-project-search`、`npm-package-search` 和 `crates-io-crate-search` 仍为 candidate。真实 `llm_live_preflight_not_ready` 或 `E_LLM_UNAVAILABLE` 会保持 `adapter_package` pending 或 blocked，并把 doctor evidence 附回公开 issue；不生成伪造 adapter asset，不将案例提前标为 active。

本版不向仓库写入 `~/.cliany-site/` runtime 状态，不创建 session、snapshot、adapter archive 或第三方业务数据。

## 风险与兼容性

- 不带 `--require-capability` 的 `doctor` 行为保持诊断兼容性，warning 仍不会使普通诊断命令失败。
- 自动化在升级后应使用 candidate promotion plan 给出的严格 command，而不是把旧的 live-only command 当作 release gate。
- 严格失败 envelope 的主要 payload 位于 `error.details`；已更新本仓库的 evidence consumers，但第三方自定义脚本需要同时处理 `data` 和 `error.details`。
- `llm_live_preflight_not_ready` 仍是 candidate blocker，不得用重试、离线 fixture 或文档修改替代真实 live 成功、adapter package 或 online smoke 证据。

## 发版步骤

1. 完成版本、CHANGELOG、官网基线、reviewed GitHub Release Notes 和本草案，在干净 HEAD 运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.278`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.278 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.278`。
5. 运行 `gh release edit v0.16.278 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.278-github-release.md`，再用 `gh release view v0.16.278 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

## Release Notes 摘要

`v0.16.278` adds a strict, evidence-preserving gate for candidate adapter generation: unavailable live providers now stop automation without discarding the doctor evidence needed to explain the blocker.
