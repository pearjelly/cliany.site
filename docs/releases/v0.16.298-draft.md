# v0.16.298 发布草案

**目标版本：** `0.16.298`
**提交范围：** `v0.16.297..HEAD`
**发布主题：** 让 HTTP API 的 liveness probe 能够识别实际运行的 cliany-site 包版本，同时保持 readiness 边界诚实。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.298..HEAD`；该锚点不改变实际 release diff。

## 用户价值

`GET /health` 以前只返回 `{"status":"ok"}`。部署脚本和 API 使用方只能知道 HTTP 进程可访问，无法从该探针确认正在运行的是哪个 cliany-site 发行版本，也容易把 liveness 错当成 Chrome/CDP 或 LLM provider 的 readiness。

本版在保留 `status="ok"` 的同时增加稳定的 `service="cliany-site"` 与 `version` 字段。`version` 是当前已安装包的版本；未找到发行元数据的源码场景安全返回 `"unknown"`，不会让 health handler 失败。双语 README 与官网清楚区分 `GET /health` 的 liveness/version 语义和 `GET /doctor` 的浏览器、配置诊断语义。回归测试覆盖已安装版本与缺失元数据两种路径。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 仍包含四个 active case、三个 candidate package-search case 和一个 `search-extraction-gap`；candidate 的九项 promotion evidence 仍为 pending。
- 2026-08-03 最近一次真实 `doctor --llm-live --require-capability generate_adapters --json` 在 Chrome/CDP 可用时仍因 provider connection error 返回可重试 `E_LLM_UNAVAILABLE`；`summary.ready_for_explore=false` 且 `generate_adapters.ready=false`。本版不运行 candidate `explore`，不生成、安装或发布 candidate adapter package，也不声称 metadata validation 或 online smoke 成功。
- 真实 blocker 摘要已写入公开 PyPI candidate issue #14；`llm_live_preflight_not_ready` 仍是 candidate adapter-package 路径的 blocker，只有严格预检变为 ready 后才能开始真实 `explore`。
- `GET /health` 只证明服务可访问及其安装版本；它不证明 third-party workflow、candidate package 或 live LLM 成功。

## 风险与兼容性

- 既有 `status` 字段、HTTP 状态码、SDK envelope 和 `/doctor` 语义不变；`service` 与 `version` 是向后兼容的新增 JSON 字段。
- `version="unknown"` 只表示当前环境找不到 distribution metadata，不是版本验证成功的替代品；发行流程仍以严格 GitHub/PyPI audit 为准。
- `/health` 是 liveness probe，不会启动或检查 CDP，也不会调用 LLM provider；调用方必须用 `/doctor` 或显式 CLI preflight 确认运行 readiness。
- 本版不代表 live LLM、candidate workflow、candidate adapter package 或第三方站点操作成功。

## 发版步骤

1. 只在下一个允许发布日完成版本、CHANGELOG、官网基线和路线图的实际 finalization，并运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.298`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.298 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.298`。
5. 运行 `gh release edit v0.16.298 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.298-github-release.md`，再用 `gh release view v0.16.298 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

## Release Notes 摘要

`v0.16.298` makes the HTTP liveness probe version-aware while preserving the boundary between service reachability and browser or provider readiness, without claiming a live provider or candidate workflow succeeded.
