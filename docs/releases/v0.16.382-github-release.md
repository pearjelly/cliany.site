# v0.16.382

## SDK and HTTP Workflow Fixes

- First SDK/HTTP generation distinguishes adapter core files from extraction-only directories, retaining the observed starting URL path and model record. Existing complete/partial core artifacts still use merge handling; explicit force remains the replacement path. Historical generated files are not rewritten.
- Typed model-service failures return the legacy SDK JSON envelope instead of escaping as exceptions or HTTP plain-text 500. Upstream HTTP 401/403 preserves `E_LLM_AUTH_FAILED`; other typed failures use `E_LLM_UNAVAILABLE`, with safe retryability, status and `llm_invoke` details.
- HTTP returns JSON with 503 for unavailable upstream dependencies, not a caller-login challenge. Read `retryable=false` and repair configuration before retrying. Fixed messages exclude upstream bodies and private endpoints; existing request budgets and retry policy are unchanged.

## Evidence and Limits

Baseline regressions retain six first-generation failures and 26 typed-error failures; retry recovery controls still passed. Actual SDK mock transports check rejection/exhaustion request counts and privacy without sending invalid real credentials. Real Chromium tests cover SDK and HTTP generation, strict verification and changed-input returned-value plus DOM checks.

One clean-source SDK Python docs generation passed after strict real preflight, preserving provenance. Six SDK/HTTP changed-query replays matched independently observed ordered 100-row prefixes and an empty normal page. Prefixes are capped, not complete collection; this is not a real HTTP-generation study, general availability/latency or independent first-user evidence. Earlier preflight failures and helper faults remain retained. See [first-generation review](https://github.com/pearjelly/cliany.site/blob/v0.16.382/docs/user-evidence/2026-10-10-sdk-first-generation.md) and [provider-error review](https://github.com/pearjelly/cliany.site/blob/v0.16.382/docs/user-evidence/2026-10-10-sdk-provider-errors.md).

CLI `ok` and SDK/HTTP `success` envelopes remain distinct. Other historical SDK error paths are unchanged; this is not a whole-SDK privacy or parity promise. Case promotion, independent first use, local HTTP security and provider-tail acceptance remain separate.
