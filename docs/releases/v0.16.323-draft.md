完成 version bump 后，target-mode readiness 使用 **提交范围：** `v0.16.322..HEAD`；创建本地 tag 后，release-tag mode 检查实际发布起点 `v0.16.322..HEAD`。

## 用户价值

- Dependabot PR #18 将 `actions/setup-python@v6` 升级为已审阅的 `actions/setup-python@v7`，覆盖 master CI、Embodied CI、依赖升级验证与 tag Release workflow。
- 本版本把这个真实已合并的维护变更纳入 strict readiness：CI 与 Release Preflight 缺少 `actions/setup-python@v7` 时会在 tag 前阻断，降低 action major 漂移和发布环境不一致的风险。
- 不改变 CLI、adapter、SDK、HTTP API、workflow job 或发布顺序；最终 master SHA 的新鲜 GitHub CI 与 Embodied CI 仍是 tag 权威。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 仍是 8 个案例、4 个 active、3 个 candidate、1 个 known-gap 的公开边界。
- `search-extraction-gap` 仍保持真实案例库中的质量回归映射。
- 最近真实 `doctor --llm-live --require-capability generate_adapters --json` 预检仍为 retryable `E_LLM_UNAVAILABLE` / `llm_live_preflight_not_ready`；没有 adapter package、metadata validation、online smoke 或 live LLM 成功证据，本版本不晋级 candidate。

## 风险与兼容性

- 变更限于 GitHub Actions 依赖版本和 readiness 文本门禁，不改变 Python runtime、adapter 文件格式、SDK、HTTP API 或 workflow job 拓扑。
- `actions/setup-python@v7` 由新鲜 CI 与 release preflight 验证；若任一必需 CI 失败，不创建 tag、不发布 GitHub Release 或 PyPI。
- 本地 workflow readiness 与发布证据不代表 Chrome、LLM、浏览器工作流或第三方服务可用。

## 发版前验证

- 运行网站 JavaScript 语法检查、相关 focused tests 和 `CLIANY_QA_OFFLINE=1` 全量测试。
- 运行 Ruff、Mypy、`uv lock --check`、strict case catalog、`uv build` 与 `uvx twine check dist/*`。
- 运行 `python scripts/release_readiness.py --strict --remote --remote-name origin`，确认版本、CHANGELOG、site、draft、workflow action major 与远程状态一致。
- 只有最终 master SHA 的 GitHub CI 与 Embodied CI 都 success 后，才允许创建本地 tag。

## 发版步骤

1. 推送最终 master，等待该 SHA 的 GitHub CI 与 Embodied CI 成功。
2. 创建 `v0.16.323`，运行带 remote 的 `--release-tag` readiness；失败时删除未推送 tag 并修复，不继续发布。
3. 推送 tag，等待 Release workflow，精确核验 GitHub Release 与 PyPI 专属版本/latest。
4. 将 `site/` 部署到 cliany.site Vercel production，执行 `vercel inspect www.cliany.site` 和真实浏览器检查。
5. 最后运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`。
