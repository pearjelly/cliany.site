# v0.16.297 发布草案

**目标版本：** `0.16.297`
**提交范围：** `v0.16.296..HEAD`
**发布主题：** 让 HTTP API 服务在 headless、Docker 和远程 Chrome 环境中按真实 CLI 契约启动。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.297..HEAD`；该锚点不改变实际 release diff。

## 用户价值

`serve` 一直会从根 CLI context 接收 `headless` 和 `cdp_url`，再传给 `APIServer`。但 HTTP API 文档以前只展示本地默认启动，用户在服务器或 Docker 中容易把根选项写到 `serve` 之后，或不知道怎样确认服务已经监听。

本版在双语 README 和官网 API 页给出三条可复制路径：默认连接、`cliany-site --headless serve --port 8080` 启动当前服务的 Chrome、以及 `cliany-site --cdp-url "ws://chrome:9222" serve --port 8080` 连接已有远程浏览器。`GET /health` 现在明确列为到达服务后的健康探针。新的 CLI regression 会拦截 `APIServer`，确认 root `--headless` 和 `--cdp-url` 以及 host、port 原样传递，而不会打开浏览器或启动真实端口。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 仍包含四个 active case、三个 candidate package-search case 和一个 `search-extraction-gap`；candidate 的九项 promotion evidence 仍为 pending。
- 2026-08-03 最近一次真实 `doctor --llm-live --require-capability generate_adapters --json` 仍因 provider connection error 返回可重试 `E_LLM_UNAVAILABLE`；本版不运行 candidate `explore`，不生成、安装或发布 candidate adapter package，也不声称 metadata validation 或 online smoke 成功。
- `llm_live_preflight_not_ready` 仍是 candidate adapter-package 路径的 blocker；只有严格预检变为 ready 后才能开始真实 `explore`。
- `scripts/audit_candidate_issues.py --repo pearjelly/cliany.site --json` 必须继续确认公开 candidate issues #14、#15、#16 为 current；HTTP API 文档不是第三方或 live provider 成功证据。

## 风险与兼容性

- `serve`、`APIServer`、SDK envelope 和 API endpoint 行为不变；本版只把已有根选项契约固定为回归测试，并将其写成可复制的部署文档。
- `--headless` 和 `--cdp-url` 都必须在 `serve` 前；文档引导用户每次选择一种浏览器管理方式，避免把“连接远程 Chrome”和“为本进程启动 Chrome”混为一谈。
- `GET /health` 只证明 HTTP 服务可访问；它不证明 CDP、LLM、candidate workflow、adapter package 或第三方网站操作成功。
- 本版不代表 live LLM、candidate workflow、candidate adapter package 或第三方站点操作成功。

## 发版步骤

1. 在干净 HEAD 完成版本、CHANGELOG、官网基线、路线图、reviewed GitHub Release Notes 和本草案，并运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.297`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.297 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.297`。
5. 运行 `gh release edit v0.16.297 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.297-github-release.md`，再用 `gh release view v0.16.297 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

## Release Notes 摘要

`v0.16.297` makes the documented HTTP API startup paths match the existing root CLI browser contract and adds a service reachability probe, without claiming a live provider or candidate workflow succeeded.
