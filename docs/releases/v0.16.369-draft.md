## 用户价值

- 干净安装不再依赖其他包间接提供 `aiohttp` 或 `PyYAML`；两者是 CLI 实际直接导入的运行时依赖。
- 保存登录态时若加密不可用，命令明确失败且不写明文 Cookie。密钥和会话文件采用原子写入及进程锁，旧版明文会话只有成功迁移后才能被使用。
- 显式指定 `browser navigate --session` 时，缺失或损坏的会话会在导航前报错；匿名生成命令仍可不带会话运行。

## 风险与兼容性

- 以前加密失败时写下的明文 Session 文件会尝试自动迁移；密钥或磁盘不可用时，登录态不会被静默加载，须恢复加密环境后重试或重新登录。
- 显式要求不存在的 Session 不再被当作匿名导航成功；生成命令对从未保存会话的公开页面保持匿名运行。
- 未扩展第三方在线可用性、真实模型发现能力或 localStorage 恢复范围。

## 发版前验证

1. 合并 PR #27、#28，核对最终 master SHA；更新版本号、锁文件、CHANGELOG 版本标题/compare links 及官网版本入口，并提交审阅后的发布说明。
2. 在最终 HEAD 运行完整离线测试、具身测试、`ruff check src/`、`mypy src/cliany_site/`、`node --check site/script.js`、案例严格校验、wheel/sdist 构建及 Twine 检查。
3. 确认该 SHA 的 master 普通 CI 与 Embodied CI 均通过；运行 strict target readiness，再创建本地 tag 并运行 strict tagged readiness。
4. 推送 tag 后核验 GitHub Release 正文/附件、PyPI 精确版本、官网 `www.cliany.site` 生产别名，以及全新克隆的远端分发审计。

## 发版步骤

1. 按 GitHub Release `publishedAt` 核对当地新发布日未触及每日三版上限，同时检查本地标签计数；确认最终 master 的普通 CI 与 Embodied CI 对应同一提交均通过。
2. 在干净工作区运行 `uv run python scripts/release_readiness.py --strict --target-version 0.16.369 --remote --remote-name origin`；通过后创建本地 `v0.16.369` tag，并以 `--release-tag v0.16.369` 重跑严格门禁，随后推送 tag。
3. 等待 release workflow 发布 GitHub Release 和 PyPI；按 `AGENTS.md` 从 `site/` 用 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 部署，再检查生产别名。
4. 最后运行严格远端分发审计，确认版本、Release notes、PyPI 文件和官网均公开可见。
