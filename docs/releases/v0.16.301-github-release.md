# v0.16.301

Turn a broken installed adapter into an actionable diagnosis.

## What Changed

- Root CLI invocation now recognizes a discovered current-schema adapter that could not be registered.
- It returns `E_VERIFY_STATIC` with the adapter domain, a loader verdict, and a concrete reason instead of an ambiguous unknown-command error.
- The response points to `cliany-site verify <domain> --strict --json` so people and automation can inspect the same strict verification result before continuing.
- Non-object metadata is reported as a schema error without blocking discovery of other adapters.

## Compatibility

Adapters that register successfully, built-in commands, and legacy-adapter migration behavior are unchanged. The only changed error path is a current-schema adapter that is present but cannot load: it now has a structured static verification response. JSON remains an error envelope with a nonzero process exit.

## Trust Boundaries

This diagnosis does not prove that CDP, a browser workflow, a third-party site, GitHub Release, PyPI publication, a live LLM provider, or a candidate adapter package is ready. It only identifies a local adapter registration problem and directs callers to strict verification. Candidate promotion remains pending until its required evidence is collected and verified.

## Verification

Focused CLI/loader/metadata regressions, full offline tests, package build and Twine validation, required CI, GitHub Release, PyPI, Vercel production deployment, website browser inspection, and strict publication audit are required before release completion.
