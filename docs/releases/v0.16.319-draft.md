## 用户价值

候选案例的公开 issue 现在把两种证据分开：尚未生成的 adapter package evidence 仍然是 pending，而已经保存并附加的 doctor preflight 会显示其 values SHA-256 和 gate 状态。provider 暂不可用时，正文明确要求等待恢复后重新运行严格 live preflight，不会把“证据已附加”误解为“adapter 已可生成”。

机器可读的 `issue_template_primary_task` 同步暴露 evidence-attached 和 public-next-action 字段，方便 issue bot、维护者和人工 Markdown 读取同一条安全边界。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 的案例入口和 8 个案例状态保持可验证；本版只改进 issue handoff，不生成、安装或晋级 candidate adapter。
- `search-extraction-gap` 仍是已知抽取缺口，本版不修改 browser、提取、adapter runtime 或在线 smoke。
- `pypi-project-search`、`npm-package-search` 和 `crates-io-crate-search` 仍是 candidate；本版不生成、安装或晋级 candidate adapter。
- 2026-08-13 的真实 strict live preflight 仍为 retryable `E_LLM_UNAVAILABLE` / `llm_live_preflight_not_ready`；`local_ready=true`、`local_blockers=[]`，但 `live_blockers=["llm_live"]`，因此 candidate adapter promotion 仍被阻断。
- 不声称 candidate package、metadata validation、online smoke、浏览器 replay 或 live LLM 成功。

## 风险与兼容性

- 不带 `--doctor-json` 的 issue template、审计、planner 和现有 package evidence 字段保持兼容。
- 预检证据已附加只改变公开交接文案和 machine-readable public-next-action，不改变 candidate 状态、严格 preflight 或 package acceptance gate。
- 本版不创建、关闭或提前晋级 GitHub issue。

## 发版步骤

1. 按实际日期完成版本、CHANGELOG、官网和 GitHub Release Notes finalization，并保持工作树干净。
2. 推送最终 master，等待该 HEAD 的 GitHub CI 与 Embodied CI 均成功。
3. 仅在双 CI 成功后运行 `git tag v0.16.319` 创建本地 tag，并运行 `python scripts/release_readiness.py --strict --release-tag v0.16.319 --remote --remote-name origin`。
4. 推送 tag，等待 Release workflow 成功，逐版本核验 GitHub Release 和 PyPI。
5. 将 `site/` 部署到明确链接的 `cliany.site` Vercel production 项目，inspect 后进行浏览器检查。
6. 运行 `python scripts/check_release_publication.py --strict --remote --distribution --json`；任一证据失败都不宣称发布完成。
