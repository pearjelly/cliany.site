## 用户价值

- 生成的列表/表格命令会等待客户端渲染结果短暂稳定；持续变化时返回 `E_PAGE_NOT_READY`，不再把正在增长的结果当成完整成功。
- 明确允许零结果的搜索/筛选工作流可保持成功语义，缺失字段仍受质量门禁约束。
- 最终命令动作分组无效时仅请求一次非执行性修正，并记录 `partition_repair_attempts`；若仍无效则失败。
- 数据命令因某字段全部为空而触发质量门禁时，一次修正反馈会点明字段，并区分页面确无可选字段与任务所需字段；不会自动放宽门禁或编造值。
- 完成门禁修正可舍弃已确认失败的旧 extract 动作，但其他动作仍必须恰好归属命令，且修正后必须有新的成功 extract；旧失败动作不会被生成命令重复执行。
- 列表提取若定位到唯一的 `<ul>/<ol>` 容器，会读取其直接列表项；零匹配时返回空数组，而不是把空容器误读为一条空数据。
- `expects_nonempty=false` 只允许列表/表格的真实空集合；请求的数量或状态文本若未提取到，探索、生成命令和 SDK 均明确失败，不再凭页面状态返回伪成功。
- 探索提示现可从增强 AX/DOM 树看到可见只读 `status`、`list` 等元素的语义和已观察到的稳定选择器；交互元素的 `selector_map` 不变。
- 无密钥首用时，`doctor` 对缺少 `AGENT.md` 的提示会明确说明不影响已有 adapter；只有要生成新 adapter 才需要先做 LLM 预检再运行 `explore`。
- 真实 Python 文档搜索成为可追踪的 candidate 案例，附带本地包和独立 DOM 核对证据，而非直接宣称 active。

## 验收证据

- PR #31 的受控本地网页基线为 8/9；后续修正路径在新的三次重放中均未触发，不能把 3/3 归因于修正机制。
- 官方 Python 文档的三次隔离 live explore 和六次变更查询 replay 均通过首 100 条标题/链接 DOM 核对；本地包独立安装后 `dataclasses` 返回 44/44 匹配行。
- `docs/user-evidence/2026-10-02-explore-replay-benchmark.md` 记录全部时延、失败与局限；这些是候选代码和当时第三方网站的证据，不是 PyPI v0.16.370 发布后验收。
- 固定提交上的 30 次受控探索/重放为 27/30（表单 10/10、筛选 7/10、语义目标 10/10），但旧基准只核对页面 DOM、未核对返回的提取值；这个分数不是端到端数据命令成功率。严格返回值口径下的筛选复测为 0/3，暴露数量选择器缺失。
- 另一次干净提交的筛选单项复测为 9/10；失败再次要求页面没有的 `url` 字段，促成本版补充具体字段的修正反馈。该反馈的实时收益仍待复测，不能把 9/10 与 7/10 合并成修复后成功率。
- 定向回归验证了“失败 extract 被新成功提取替换”和“必要动作不可遗漏”；完整离线套件为 3,163 项通过。实时模型两次预检均在 120 秒超时、没有产生修正后试验，因此不能宣称该机制已改善线上成功率。
- 服务恢复后，在修正提交上追加的 10 次筛选实测仅 6/10：一次未生成命令、一次 300 秒超时、两次零匹配重放被质量门禁明确拒绝。14 次成功返回的重放均通过独立 DOM 核对；没有证据表明失败 extract 恢复路径在真实模型中触发，不可宣称修正提高了成功率。
- 后续筛选诊断为 1/3，两次失败均选择了 `<ul>` 结果容器并在零匹配时生成一条空行；针对容器的 Chromium 回归已覆盖修复前后的行为。新提交的筛选小样本为 3/3，但均未选中容器，不能单凭该样本归因；此前失败仍计入整体证据。
- 收紧门禁后、加入只读候选前的严格筛选复测为 0/3，三次都在探索阶段以 `E_EMPTY_RESULT` 明确失败，而非生成缺少数量的命令；这一结果定位出当时的只读元素选择器缺口。
- 加入增强树只读候选后，干净提交的严格筛选复测为 3/3；三次均使用实际存在的 `#summary`，六次正向/零匹配重放的返回值与独立 DOM 均通过。完整三任务 3×3 严格矩阵两次预检超时、没有产生试验，不能把筛选 3/3 外推到其他工作流。
- `docs/user-evidence/2026-10-02-jira-pypi-demo-audit.md` 补记了 PyPI v0.16.368 在全新 Python 3.11 环境中的无密钥首用和 Jira REST 独立核对；这是维护者测试，不是独立用户采纳证据。
- PR #31 当前普通 CI、Chromium embodied CI 均通过；本分支和最终 master 仍须重新验证。

## 风险与兼容性

- 四次相同采样只是有界稳定性启发式，不保证任何异步网页已经完成；返回结果仍最多 100 条。长期活跃列表会增加最长约六秒的采样等待后明确失败。
- 零匹配时唯一的语义列表容器现在返回空数组；其他来源的字段全空伪结果行仍会触发 `E_EMPTY_RESULT`，不会把部分提取降级为合法空结果。筛选生成命令在小样本中仍不稳定。
- 增强树候选后严格筛选为受控 3/3，但未完成完整跨任务严格矩阵，也未在公开站点验证这一只读目标定位路径；不能用小样本或页面 DOM 通过率宣称普遍可靠。
- 公共文档页的结构或站点可用性可能变化；当前 3/3 不是广泛可靠性估计，也没有独立新用户的成功证据。
- Python 文档 adapter 归档当前只在本地，正式 Release 上传及下载后的严格校验尚未完成，不可晋级 active。

## 发版前验证

1. 先完整发布 v0.16.369，再合并 #31 和本候选；把提交范围更新为 `v0.16.369..HEAD`，核对最终 master SHA 与当日 GitHub 发布额度。
2. 在最终 HEAD 运行完整离线测试、Chromium embodied 测试、`ruff check src/`、`mypy src/cliany_site/`、`node --check site/script.js`、案例严格校验、wheel/sdist 构建和 Twine 检查。
3. 确认最终 master 的普通 CI 与 Embodied CI 都通过，运行严格 target readiness；创建本地 tag 后运行严格 tagged readiness。
4. 发布后检查 GitHub Release notes/assets、PyPI 精确版本、官网 `www.cliany.site` 生产别名和全新克隆远端分发审计。另行上传 Python 文档 adapter 资产并完成固定 SHA 公开下载、严格校验与独立重放，未完成则保持 candidate。

## 发版步骤

1. 运行在线 `scripts/check_github_release_cap.py --strict --json`，核对上海时间当天实际 GitHub Release 数，未空出额度不得继续。
2. 在干净的最终 master 工作区运行 `uv run python scripts/release_readiness.py --strict --target-version 0.16.370 --remote --remote-name origin`；通过后创建本地 `v0.16.370` tag，再用 `--release-tag v0.16.370` 重跑严格门禁，最后推送 tag。
3. 等待 release workflow 发布 GitHub Release 和 PyPI；从 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 并检查生产别名。
4. 运行严格远端分发审计。Python 文档 adapter 包须按其已记录的 SHA-256 单独上传、下载、安装和在线核对后，才能更新案例状态。
