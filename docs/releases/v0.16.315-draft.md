# v0.16.315 发布草案

**目标版本：** `0.16.315`
**计划日期：** 2026-08-12
**提交范围：** `v0.16.315..HEAD`
**发布后范围：** `v0.16.315..HEAD`

完成 version bump 后，target-mode readiness 使用 **提交范围：** `v0.16.315..HEAD` 作为占位锚点；创建本地 tag 后，release-tag mode 检查实际发布起点 **提交范围：** `v0.16.314..HEAD`。实际 release diff 是 `v0.16.314..v0.16.315`。

## 用户价值

当维护者将真实 `doctor --llm-live --require-capability generate_adapters --json` 证据传给 `cliany-site cases --issue-template --doctor-json ...` 时，v0.16.315 会在 Primary Evidence Task 的可执行命令之前显示当前 gate、adapter package 是否可运行、阻断原因与所需下一步。对应 JSON primary task 同时提供扁平字段，方便自动化读取同一结论。

这也覆盖严格 doctor 失败 envelope：运行时诊断位于 `error.details` 而非顶层 `data` 时，issue template 仍显示真实的 blocked state，而不是让后续 `explore` 命令看起来已经可执行。

## 案例库映射

- `cases/README.md` 与 `cases/manifest.json` 的 8 个案例状态不变；本版不生成或安装 candidate adapter。
- `search-extraction-gap` 仍是已知缺口，本版不修改 browser、提取、adapter runtime 或在线 smoke。
- 2026-08-12 的真实 live preflight 返回 retryable `E_LLM_UNAVAILABLE`，归类为 `llm_live_preflight_not_ready`；本地 `local_ready=true`、`local_blockers=[]`，但整体 gate 仍是 blocked。
- 因此不声称 candidate package、metadata validation、online smoke、浏览器 replay 或 live LLM 成功。

## 风险与兼容性

- 未传入 `--doctor-json` 时，既有 issue template 输出保持不变。
- 传入可验证 evidence 时仅补充交接摘要；候选任务、runbook、case 状态和实际 `explore` 命令都不被自动执行或改写。
- 严格 error envelope 继续复用既有 evidence loader，不把 `E_LLM_UNAVAILABLE` 变成健康状态。

## 发版步骤

1. 完成版本、CHANGELOG、官网与 release notes finalization，并保持工作树干净。
2. 推送最终 master，等待该 HEAD 的 GitHub CI 与 Embodied CI 均成功。
3. 仅在双 CI 成功后创建本地 `v0.16.315` tag，并运行 strict `--release-tag` readiness（含 remote）。
4. 推送 tag，等待 Release workflow 成功，逐版本核验 GitHub Release 与 PyPI。
5. 将 `site/` 部署到明确链接的 `cliany.site` Vercel production 项目，浏览器检查 `www.cliany.site`。
6. 运行 strict publication audit；任一证据失败都不宣称发布完成。
