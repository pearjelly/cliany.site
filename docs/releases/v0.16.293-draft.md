# v0.16.293 发布草案

**目标版本：** `0.16.293`
**提交范围：** `v0.16.292..HEAD`
**发布主题：** 让 candidate 案例的 future adapter 命令不会被误认为当前可运行 demo。

完成 version bump 后，target-mode readiness 还会检查占位锚点 **提交范围：** `v0.16.293..HEAD`；该锚点不改变实际 release diff。

## 用户价值

`cliany-site cases --status candidate` 以前会在“快速命令”中先展示 live LLM preflight 和 `explore`，随后无标签地打印 future adapter 的 online smoke 命令。当前三个 candidate 都没有已发布 adapter package、metadata validation 或 online smoke 证据，用户却可能把最后一条命令当作可立即执行的 demo。

本版保留 candidate 的晋级任务和命令契约，但在人类输出中把 future adapter 命令明确标为“当前不可运行”。只有 adapter package 已发布、安装并通过 `verify --strict` 后，它才成为可执行命令；active demo 的快速路径不变。

官网 quickstart 也曾在普通 `cliany-site doctor` 之后直接引用 JSON-only 的 `data.summary.demo_adapter_quickstart.recommended_commands`。本版将人类和自动化路径分开：人类用户复制 doctor 实际打印的有序命令，自动化才显式运行 `cliany-site doctor --json` 并读取 JSON 字段。

## 案例库映射

- `cases/manifest.json` 与 [cases/README.md](../../cases/README.md) 仍包含四个 active case、三个 candidate package-search case 和一个 `search-extraction-gap`；candidate 的九项 promotion evidence 仍是 pending。
- 2026-07-31 对 `cliany-site doctor --llm-live --require-capability generate_adapters --json` 的真实预检显示 Chrome/CDP、key 和 provider 配置可用，但 live LLM preflight 因可重试的 `E_LLM_UNAVAILABLE` connection error 阻断 `generate_adapters`。
- 因 preflight 未 ready，本版不运行 candidate `explore`，不生成、安装或发布 adapter package，也不声称 metadata validation 或 online smoke 成功。
- `scripts/audit_candidate_issues.py --repo pearjelly/cliany.site --json` 仍确认公开 candidate issues #14、#15、#16 为 current；本地 preflight 证据未写入公开评论。
- 在没有 ready 预检时，release handoff 仍必须保留 `llm_live_preflight_not_ready` blocker，而不是把 candidate adapter package 视为已完成。

## 风险与兼容性

- JSON `commands`、promotion command plan、issue template 和 evidence bundle schema 均不变。
- Candidate 的 preflight 和 `explore` 任务仍可作为明确的晋级步骤阅读；仅 future adapter 命令新增人类可读的不可运行边界。
- 该标签不是 adapter 已安装、可验证或能够访问第三方站点的声明。
- 普通 `doctor` 命令的输出 schema 与建议内容不变；本版只在官网和 quickstart 中停止把 JSON 字段描述为 human output。

## 发版步骤

1. 在干净 HEAD 完成版本、CHANGELOG、官网基线、路线图、reviewed GitHub Release Notes 和本草案，并运行 target-mode readiness。
2. 推送最终 `master` 后，等待 GitHub CI 与 Embodied CI 都成功；任一失败都不创建 tag。
3. 仅在 CI 成功后创建本地 `git tag v0.16.293`，运行 `uv run --extra dev --frozen python scripts/release_readiness.py --strict --release-tag v0.16.293 --remote --remote-name origin`。
4. 通过 tag gate 后推送 tag，等待 GitHub Release workflow，逐版本检查 GitHub Release 与 PyPI `0.16.293`。
5. 运行 `gh release edit v0.16.293 --repo pearjelly/cliany.site --notes-file docs/releases/v0.16.293-github-release.md`，再用 `gh release view v0.16.293 --repo pearjelly/cliany.site --json body` 检查 release notes。
6. 在 `site/` 运行 `vercel link --yes --project cliany.site`、`vercel --prod --yes` 与 `vercel inspect www.cliany.site --wait --timeout 90s`，然后浏览 www.cliany.site。
7. 运行 `uv run --extra dev --frozen python scripts/check_release_publication.py --strict --remote --distribution --json`；audit 成功后才报告完成。

## Release Notes 摘要

`v0.16.293` makes candidate handoffs distinguish a future adapter command from a currently runnable active demo, without changing candidate evidence or claiming a live workflow succeeded.
