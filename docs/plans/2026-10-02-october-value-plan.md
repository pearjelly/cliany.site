## Product outcome

A new user should be able to install the public package, obtain one useful read-only result, and trust a command generated from a browser workflow enough to reuse it with a changed input. Count success only when a fresh environment and an independent business-result check agree; passing tests, a generated adapter file, or a successful JSON envelope alone are insufficient.

## Evidence at the decision point

- Four maintained active cases exist. Published-package, fresh-HOME demos have returned nonempty Jira and Confluence results; the Jenkins first-result path also passed a published-package check. A maintainer installed PyPI v0.16.369 into a clean Python 3.11 environment and obtained five Jira issue rows. The merged [doctor first-result change](https://github.com/pearjelly/cliany.site/pull/42) then suggested one `demo` command, which also installed the adapter and returned five rows in an isolated HOME. These are maintained read-only integrations and maintainer checks, not independent-user acceptance or proof that a live model discovered a public browser workflow.
- The early 8/9 controlled sample checked replay page state but not returned extract values, so it is not an end-to-end data-command score. Later strict output-plus-DOM matrices on draft v0.16.370 commits varied from 4/9 to 9/9. The predeclared fixed-commit study of 10 fresh trials per task scored **25/30**, below the 27/30 target: four explorations timed out at 300 seconds, and one semantic command partition remained invalid after its one correction. All 34 changed-input replays from the 25 successful trials matched returned values and independent DOM; no silent wrong success was observed. Exploration p50 was 103.41 seconds and nearest-rank p95 was 300.03 seconds. Reliability and generation latency remain open; [PR #34](https://github.com/pearjelly/cliany.site/pull/34) retains the detailed evidence.
- A fresh [published-v0.16.371 controlled baseline](../user-evidence/2026-10-03-v371-controlled-baseline.md) on clean master `779e592` scored **4/9** with strict returned-value plus DOM checks: form 2/3, filter 0/3, semantic 2/3. All 11 replay pages reached the expected DOM state, but seven returned-value checks failed, exposing wrong-success risk in generated extraction. One form explore hit 300 seconds. This is a different codebase and small sample, not a causal comparison with draft PR #34.
- On now-merged [#47](https://github.com/pearjelly/cliany.site/pull/47), earlier clean fixed-commit 30-trial samples scored **25/30**, **27/30**, **28/30**, **22/30**, **21/30**, **24/30**, and **30/30** with returned-value plus DOM oracles. A clean fixed-head sample on `4d90e3c` scored **30/30** with all 40 changed-input replays matching returned values and independent DOM, zero silent wrong successes, median exploration 15.3 seconds, and p95 186.4 seconds. No trial used command-partition repair, so the score does not prove that repair's live effectiveness. Score movement across samples cannot be attributed to one change; latency and independent-user acceptance remain open. Do not turn controlled evidence into a general success-rate claim.
- PyPI search reached `Client Challenge`; npm reached a Cloudflare challenge; crates.io timed out or returned HTTP 403 from the maintainer network. Their cases remain candidates. Do not bypass site restrictions or promote them on package verification alone.
- A [Python documentation browser candidate](../user-evidence/2026-10-03-python-docs-browser-candidate.md) has three clean, isolated live explorations on commit `2ec4f83`, strict verification, changed-query replays, and independent browser checks of first title/link and final page counts. Extraction returns at most 100 rows, below each tested page's final count. Its [public adapter archive](https://github.com/pearjelly/cliany.site/releases/download/v0.16.373/docs.python.org-0.1.0.cliany-adapter.tar.gz) has a recorded SHA-256 and passed install, strict verify, and changed-query replay using the published PyPI package with an isolated cliany runtime directory. A wholly synthetic OS `HOME` hit first-navigation timeouts in two maintainer attempts; split-environment controls point to Chrome's launch environment on this macOS host, with the exact cause still open in [Issue #53](https://github.com/pearjelly/cliany.site/issues/53). No independent-user result exists, so it remains a candidate. Earlier failed trials and the partial-result bug are recorded in the evidence note.
- A later [published-v0.16.374 replay](../user-evidence/2026-10-04-v374-python-docs-replay.md) installed and strictly verified the unchanged public archive in a temporary CLI home while Chrome ran with the normal OS home. `pathlib` and `asyncio` returned capped nonempty results with expected first links; a zero-match query exited nonzero with `E_EMPTY_RESULT`. A separate browser confirmed the `asyncio` first link and zero-match list state. This is another maintainer-only check, not independent-user acceptance or proof that all matching pages were returned.
- No independent first-time user's end-to-end quickstart result has been recorded. The published browser-adapter trial requests feedback in [Issue #55](https://github.com/pearjelly/cliany.site/issues/55), which has no user report yet. The historical Q3 plan's 1.0-alpha checkpoint is therefore not evidence of alpha readiness.

## Release discipline

Keep the user-requested daily verified release cadence, with at most three public releases on a Shanghai calendar day. A release is complete only after GitHub Release, PyPI, and the production website agree on the exact version and a fresh remote audit succeeds. Work waiting behind the daily cap stays in reviewed PRs, not as an unverified tag. Default PR CI remains offline with no real LLM key; live-provider and third-party runs are explicit, bounded evidence tasks.
