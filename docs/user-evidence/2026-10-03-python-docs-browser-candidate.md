# Python docs browser candidate (2026-10-03)

This note began with one maintainer-run, read-only third-party browser trial on draft PR #47. It now records later trials and a public adapter archive, but no independent-user result. The starting page was `https://docs.python.org/3/`. A fresh browser showed the normal Python documentation and a working Quick search form without login or a challenge.

With an isolated runtime directory (`/tmp/cliany-public-python-20261003-1`), headless Chrome, and the live provider, `explore` searched for `asyncio` and generated one `search-docs --query` command in about 52 seconds. `verify docs.python.org --strict --json` returned `verdict=ok`; its report also noted that no market manifest exists. Replaying the generated command with changed input `pathlib` returned `ok=true`, an `ok` list extraction with 100 rows, and first row `title=pathlib`, `url=library/pathlib.html#module-pathlib`. An independent browser submitted `pathlib` through the site's own Quick search form and showed the same first result title and relative link. The page reported 131 matching pages, so this check does not establish complete collection of all results.

Two limitations block promotion. The generated extract action used `#search-results li` with `a` and `a@href` fields, but the saved selector pool was empty; this trial has not shown an AXTree-grounded semantic extract target. It also comprises only one fresh exploration, not the three required by the October plan. Do not publish the adapter or count this as a maintained browser case yet.

The trial exposed an isolation defect: exploration saved its Markdown extract under the user's normal `~/.cliany-site/adapters/docs.python.org/extracts/` despite the isolated runtime directory. The exact file created by this run was removed; two older files in that directory were left untouched. A focused test reproduced the defect, and the writer now uses the configured `adapters_dir` for its default path. The fix passed 3196 offline tests, 28 embodied tests, Ruff, and mypy. A direct save using an overridden runtime home wrote only under `/tmp/cliany-public-python-20261003-2/adapters/docs.python.org/extracts/`.

A second fresh, isolated live exploration searched for `pathlib`. It completed the search and extraction steps, but the third model call remained in flight beyond about five minutes. The run was interrupted and returned `E_UNKNOWN`; Chrome exited and the user's normal extract directory gained no new file. Because exploration never reached its final save, this is a failed trial, not live confirmation of the path fix or a second successful browser case. No retry was run to replace it.

On a later draft, the browser extractor was extended to derive `#search-results li` only when an observed stable parent directly contains one semantic `ul`/`ol` list. A fresh read-only browser check of `https://docs.python.org/3/search.html?q=pathlib` found a normal results page with a `div#search-results`, one direct child `ul`, and 131 `li` elements. A separate browser-use CDP AX capture on that page returned three read-only candidates, including `{"role":"list","selectors":["#search-results li"]}`. This is new grounding evidence for the selector on the current page, not retroactive proof that the earlier generated adapter was grounded, nor proof of complete 131-row collection (the runtime caps lists at 100). No new live explore/replay or distributable package was produced. The full-site AX snapshot in Playwright CLI timed out, so the structural check used targeted DOM inspection and the separate CDP AX capture instead; neither required login or a challenge.

The shared list/table field extractor previously substituted the entire row text when a requested text child was missing, and could substitute a neighboring or parent link when a requested `@href` child was absent. A Chromium regression using `search_extraction_gap.html` reproduced a missing second-row URL incorrectly returning the first row's URL. The draft now reads only the requested child or the row itself when the field spec explicitly has no child selector; missing fields stay blank and trigger partial-quality diagnostics. This fixes that false-success path on the fixture but does not establish the Python documentation case's generated-field accuracy. Fresh explore/replay evidence is still required.

On 2026-10-04, a fresh isolated exploration on draft PR #47 generated and strictly verified a `search-docs --query` command from `https://docs.python.org/3/`. Its changed-input replay for `pathlib` returned `ok=true` with only three list rows, even though an independent browser showed the same page still labeled `Searching` and later showed 131 results. A measured fresh search for `asyncio` grew from 1 to 399 list rows over about three seconds before the heading became `Search Results`. The runtime's fixed 1.5-second pre-extract delay therefore allowed a valid-looking partial prefix. This trial is **not** a passing third-party acceptance result.

A first draft fix added bounded list settling to direct action replay; a Chromium fixture reproduced the early-prefix bug before the fix and returned all eight incremental rows afterward. A dirty-head replay of the existing `pathlib` adapter returned 100 rows, but a later clean trial exposed that generated adapters use the separate `browser extract` atom path. That earlier diagnostic was not enough to prove the generated-command route.

On clean `052ba45a588e30aef7ff3b6f62587332408b68c5`, one fresh `asyncio` exploration took about 363 seconds, passed strict verification, and replayed changed input `pathlib` with 100 capped rows; an independent browser showed 131 completed rows and the same first title and link. A second fresh `pathlib` exploration passed strict verification, but changed-input `typing` replay returned only 10 rows while an independent browser completed at 521. This is a **failed acceptance trial** despite `ok=true` and a matching first link. The atom path retried only empty lists, not valid-looking partial prefixes. The settling helper is now shared between direct action replay and the `browser extract` atom; both have Chromium regressions, and an atom-path diagnostic replay of `typing` on the dirty candidate returned 100 capped rows with the independently observed first link. Failed settling returns `E_PAGE_NOT_READY` rather than partial success. The clean three-trial gate must restart on the shared-fix commit; neither a distributable package nor an independent first-user result has been produced.

The first fresh exploration on clean shared-fix commit `a678e0e` rejected its extract selector because the AX candidate was absent during the search-page transition. No adapter was accepted from that run. A bounded AX-only recheck now waits up to eight seconds for the observed semantic candidate before allowing extraction; it still rejects an ungrounded selector. Focused tests, mypy, and exact-commit PR CI passed on `2ec4f83`.

On clean `2ec4f83`, three new isolated, live-provider explorations succeeded: `asyncio` to changed `pathlib` (about 31 seconds), `pathlib` to changed `typing` (about 26 seconds), and `typing` to changed `subprocess` (about 60 seconds). Each generated one command, passed `verify --strict`, and replayed with `ok=true`, extract quality `ok`, and 100 rows. Independent browser searches completed at 131, 521, and 170 rows respectively, with matching first title and relative URL for each changed query. These are three maintainer trials on one site, not a general reliability estimate; the 100-row extraction cap is still a product limitation.

The third adapter was packaged locally as `docs.python.org-0.1.0.cliany-adapter.tar.gz` with SHA-256 `29f1ece48fd6749e53cf7384f5be0878c1617d1d8344641e284b6c37150f6592`. A separate empty runtime home installed that archive, passed strict verification including manifest checks, and replayed changed `pathlib` with 100 rows and the independently observed first title/link. At that point the archive was not public.

After [v0.16.373](https://github.com/pearjelly/cliany.site/releases/tag/v0.16.373) was published, the same archive was attached at [the public adapter URL](https://github.com/pearjelly/cliany.site/releases/download/v0.16.373/docs.python.org-0.1.0.cliany-adapter.tar.gz). The downloaded asset's SHA-256 matched `29f1ece48fd6749e53cf7384f5be0878c1617d1d8344641e284b6c37150f6592`. A fresh Python 3.11 environment installed `cliany-site==0.16.373` from public PyPI, then installed that URL into an isolated cliany runtime directory, passed strict manifest verification, and replayed changed `pathlib` with extract quality `ok`, 100 capped rows, and the independently observed first title/link. This was a maintainer smoke with the normal OS `HOME`, run outside the source checkout.

Two attempts with a wholly synthetic OS `HOME` also installed and strictly verified the public archive but failed on the first browser navigation with `E_PAGE_NOT_READY`; one used browser-use 0.13.10 and the other 0.12.4. The successful isolated-runtime replay means the public distribution path works in the tested maintainer environment, not that a synthetic OS home or an independent user's environment works. The navigation failure needs separate diagnosis. Keep the adapter a candidate until an independent first-time user completes the path; the 100-row cap remains a limitation.
